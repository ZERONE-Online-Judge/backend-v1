# ZOJ problem archive v1

A `.zoj.zip` file contains one problem and its complete registered files. It can be imported into another division or contest. The ZIP has `manifest.json` at its root and binary members referenced by the manifest. UTF-8 JSON preserves the problem statement exactly, including the `<!--ZOJ_META:...-->` examples, input/output description, and notes. External URLs are preserved as links, never fetched by the server.

## Manifest

- `format`: `"zoj-problem"`; `version`: integer `1`.
- `problem`: `problem_code`, `title`, `statement`, `editorial`, `time_limit_ms`, `memory_limit_mb`, `language_resource_limits`, `display_order`.
- `assets`: all registered files, each with `id` (`asset-1`, etc.), `file` (ZIP member path), `original_filename`, `mime_type`, `category`, `asset_status`, `created_at` (ISO 8601). Statement/editorial references use `asset://asset-1`. The importer creates new IDs and rewrites these references, including examples stored inside the statement metadata.
- Asset categories: `assets`; `package-files/` followed by `main-solution`, `brute-solution`, `wrong-solution`, `checker`, `validator`, `generator`, `manual-input`, `test-script`, `package-resource`, or `interactor`; or `verification-solutions/` followed by `accepted`, `wrong_answer`, `time_limit_exceeded`, or `memory_limit_exceeded`.
- `testcase_sets`: all versions, not just the active one. Each has positive integer `version`, boolean `is_active`, and `testcases`. At most one version can be active.
- Each testcase has positive integer `display_order`, `input` and `output` member paths, and nullable `time_limit_ms_override` and `memory_limit_mb_override`. Display order must be unique within its version.
- `files`: exact inventory of binary members with `path`, byte `size`, and lowercase hexadecimal `sha256`. Empty files and original line endings are preserved. A member can be referenced by multiple assets/cases. Every binary member must be referenced, and every reference must exist.

The ZIP contains no passwords, signed download tokens, account information, participant submissions, judge caches, execution history, or browser-only drafts. Saved verification source files are included; previous verification results are not. Importing does not execute, compile, or revalidate source programs.

## Import and validation

The operator first uploads the ZIP to inspect it, then uploads the same selected file when confirming registration. This avoids retaining an unclaimed server-side upload. Both passes validate structure, lengths, CRC, SHA-256, references, and version. The selected division must belong to the destination contest. An existing problem code causes HTTP 409; no existing problem is overwritten. The new problem defaults to the end of its division's list. A second validation of the contest schedule occurs inside the registration transaction.

IDs and storage keys are always generated by the server. Asset categories and the relative creation times are preserved so the existing checker/validator selection continues to work. File writes are streamed and compensated on failure; all database rows are committed together. When an active testcase set is restored, the same transaction queues automatic judge-bundle generation. The existing bundle worker builds the bundle in the background and retries failures; without an active set there is nothing to bundle. An upload/storage error leaves no partial problem or queued bundle job. Failures deleting temporary objects are logged for recovery.

Limits: compressed upload 512 MiB, aggregate uncompressed 2 GiB (including the manifest), binary member 256 MiB, manifest 8 MiB, ZIP members 20,000, testcase versions 1,000, testcases across all versions 10,000. The ZIP uses stored or DEFLATE compression and a standard central directory; ZIP64 local members are supported. Encrypted, split, duplicate-path, traversal, directory, and special-file entries are rejected. Processing is limited to two simultaneous archive operations per API worker; temporary files are removed on completion/disconnect.

Exports require `contest.problem.resource.view`. Inspection/import require `contest.problem.manage` and are unavailable during a running contest. Import actions appear in the operator audit log. Images previously saved as signed storage URLs are rewritten into portable asset references when the exact object belongs to the exported problem.

## API

- `GET /api/operator/contests/{contest}/problems/{problem}/archive`: authenticated ZIP download, attachment response, no-store cache policy.
- `POST /api/operator/contests/{contest}/problem-archives:inspect`: ZIP request body with `Content-Type: application/zip`; returns content summary.
- `POST /api/operator/contests/{contest}/problem-archives:import?division_id=...&problem_code=...`: same ZIP request body; returns the new problem. Optional positive `display_order` can override append order.

Keep an unmodified exported ZIP as the reference example when authoring files outside ZOJ. Unknown manifest fields or unsupported versions are rejected rather than partially interpreted.
