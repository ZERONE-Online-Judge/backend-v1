# Editor 실행과 노드별 큐 선택

관리자 **채점 관리 → 채점 노드 현황 → 처리할 작업**에서 ZOJ와 Editor를
각각 선택합니다. ZOJ만, Editor만, 둘 다의 세 조합을 지원하며 적어도 하나는
선택해야 합니다. 설정은 DB에 저장됩니다. 에이전트 재등록이나 하트비트는
설정을 변경하지 않습니다. 서비스 마스터만 저장 API를 사용할 수 있습니다.

ZOJ는 참가자 제출·운영자 재채점·ZOJ 검증 AI의 실행입니다. Editor는 Editor
풀이의 대회 판정 검증과 컴파일·생성기·Validator·Checker·스트레스 테스트·
대화형 실행·지문 PDF의 제작 실행입니다. 패키지와 HTML 구성, 파일·DB 저장은
Editor 서버가 맡습니다. 업로드한 코드와 xelatex 실행은 채점 VM이 맡습니다.

서버의 claim 트랜잭션은 DB의 현재 처리 범위를 검사합니다. 클라이언트가
다른 큐를 요구하거나 재등록해도 범위를 넓힐 수 없습니다. 세 큐의 실행 수를
함께 세고 노드의 전체 슬롯 안에서 배정합니다. 배정은 DB의 활성 리스로
계산하며, 늦게 도착한 하트비트가 완료된 작업의 슬롯을 막지 않습니다. 노드 행 잠금과 skip locked로
중복 배정과 슬롯 초과를 막습니다. 둘 다 선택한 노드는 ZOJ 대회 큐를 먼저,
Editor 제작 실행과 Editor 최종 판정 큐를 다음으로 확인합니다. 이미 배정한
실행은 범위를 바꾸어도 계속 처리합니다. 이후 요청은 허용된 노드로 갑니다.
모든 노드의 Editor 선택을 해제하면 새 Editor 요청은 503으로 안내됩니다.

## 실행 경로

1. Editor가 문제 작업 사본과 실행 이력을 저장합니다.
2. 코드 실행마다 명령·제한·실행 파일의 SHA-256 ZIP을 준비합니다.
3. 기존 Editor HMAC/nonce 인증으로 ZOJ의 별도 제작 실행 큐에 요청합니다.
4. Editor가 허용되고 editor-execute-v1 런타임이 준비된 노드만 가져갑니다.
5. 노드는 고정 이미지 digest의 별도 컨테이너에서 실행합니다.
6. 원본 결과와 출력·컴파일 산출물을 인증된 리스로 반환합니다.
7. Editor가 검증한 산출물을 보관하고 기존 생성 결과 반영·커밋을 적용합니다.

제작 실행은 대회 제출이나 스코어보드에 들어가지 않습니다. 현재 지원하는
7개 작업 종류와 grader·파일 입출력·그룹 점수·대화형 기능을 유지합니다.
최종 풀이를 ZOJ 판정 방식으로 요청한 경우 기존 isolate 채점과 언어별 시간·
메모리 보정을 유지합니다. 제작용 격리 실행은 원래 Editor 실행 규칙을 씁니다.
각 실행의 노드·버전·CPU 시간·메모리는 Editor 결과에 함께 저장됩니다.

실행 컨테이너에는 네트워크·호스트 파일·Docker 소켓·서비스 키를 제공하지
않습니다. 컨테이너의 파일시스템은 읽기 전용이며 코드 UID와 감독 UID를
분리합니다. CPU·메모리·PID·출력과 산출물을 제한합니다. Docker 소켓은 이미
호스트 제어 권한이 있는 신뢰된 judge-agent 관리자 프로세스에만 전달합니다.
입력 파일 64MiB, 압축/전송 128MiB, 산출물 32MiB의 상한을 검증합니다.

리스를 3초마다 갱신하며 취소·노드 인증 해제·리스 변경 시 컨테이너를 종료합니다.
오래된 리스는 최대 3회 재배정하며, 반복 실패는 시스템 실행 오류가 됩니다.
임시 전송 자료와 실행 결과는 종료 48시간 후 정리합니다. Editor의 문제 자료와
전체 작업 이력은 별도로 유지됩니다. 결과 대기는 긴 GET 요청으로 처리해
반복 인증·HTTP 요청을 줄입니다.

### 업로드 중 계정 잠금과 재시도

풀이 채점과 제작 실행은 짧은 DB 트랜잭션으로 `uploading` 요청과 파일
참조를 예약합니다. 계정 잠금과 DB 연결을 반환한 뒤 파일을 저장하고,
모든 파일이 준비된 요청만 `waiting`으로 바꿉니다. 업로드 중인 요청도
계정별 한도에 포함하며, 채점기는 가져가지 않습니다.

저장 중 연결이 끊기면 같은 operation ID·자료 해시로 이어서 저장합니다.
실패했다고 공유 파일을 지우지 않으며, 미완료 예약과 파일은 기존 만료·정리
정책으로 회수합니다. 업로드 중 취소된 요청은 완료 후에도 실행하지 않습니다.
응답을 잃어 실행 ID를 받지 못한 풀이 요청도 서명된
`DELETE /api/editor/judge/run-operations/{operation_id}`로 취소할 수 있습니다.
이 변경은 DB 마이그레이션이나 채점기 업데이트가 필요하지 않습니다.

## 배포 순서

1. ZOJ 백엔드와 0049_editor_execution_tasks 마이그레이션을 먼저 적용합니다.
2. 각 사용할 채점 VM의 새 agent 체크아웃에서
   `sudo bash deploy/prepare-editor-runtime.sh`로 실행/PDF 이미지를 준비합니다.
3. 해당 노드를 비운 뒤 기존 Compose 환경·VM CPU/메모리 제한을 유지하며
   agent 0.2.22를 빌드·재생성합니다. Docker 소켓 마운트가 필요합니다.
4. 관리자에서 해당 노드의 Editor를 체크하고 런타임 준비 표시를 확인합니다.
5. Editor 백엔드, ZOJ/Editor 프런트엔드를 적용합니다.

Editor 운영 워커는 EDITOR_EXECUTION_TRANSPORT=agent로 실행하며 Docker 소켓을
마운트하지 않습니다. 로컬 개발과 기존 격리 회귀 테스트에서만 local 모드를
사용합니다. 배포 전에 실제 실행 가능한 Editor 노드가 있는지 확인해야 합니다.

내부 연결은 기존 `https://10.10.10.110:6443/api`와 CA 검증을 유지합니다.
`JUDGE_OBJECT_URL_ORIGINS`는 기존 공용 MinIO URL을 이 내부 주소로 매핑합니다.
제작 산출물 전용 내부 경로만 128MiB를 허용하고 다른 judge 요청은 4MiB를
유지합니다. 구버전 에이전트는 기존 최종 판정만 받을 수 있고 제작 실행을
가져가지 않습니다. 기능 브랜치 구현만으로 운영 노드가 업데이트되지는 않습니다.
