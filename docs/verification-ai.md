# 검증 에이전트

문제 관리 → 테스트케이스 → 검증 코드에서 기대 판정과 실제 판정이 다른 코드에서 **AI 분석하기**를 누르면 필요한 자료를 찾아 읽고, 기존 채점기로 원본과 수정 후보를 실행합니다. 결과·후보 코드·실행 기록을 DB에 보관해 다른 권한 있는 운영자도 볼 수 있습니다. 원본 코드와 공식 판정, 문제 파일은 변경하지 않습니다.

## 문제별 자유 요청

문제 관리 → **검증 에이전트**에서 자연어로 목표를 입력할 수 있습니다. 예를 들어 checker의 오판, validator의 경계값 처리, 두 풀이의 불일치, 테스트 누락을 맡길 수 있습니다. 오답 판정이나 기존 검증 제출이 없어도 시작됩니다. 저장된 문제 자료의 스냅샷을 작업 기준으로 삼고, 코드는 선택 사항이며 에이전트가 등록 자료에서 필요한 코드를 고를 수 있습니다.

- 모델이 `update_plan`으로 작업 계획을 만들고 자료 조회·파일 편집·실험·실제 채점 도구를 선택합니다. `record_finding`은 확인된 사실·가설·기각한 가설과 실제 파일/실행 ID를 보관합니다. 공개 작업 요약이며 내부 사고 과정은 저장하지 않습니다.
- `list_verification_runs`와 `read_verification_run`으로 현재 문제의 기존 검증 코드 제출·채점 당시 소스·로그를 찾을 수 있습니다. 참가자의 일반 제출 조회 권한을 새로 부여하지 않습니다.
- `ask_user`는 사용자만 정할 수 있는 조건을 질문하고 `awaiting_input`으로 대기합니다. 기다리는 동안 모델을 호출하지 않습니다. 답변 또는 추가 요청은 부모 작업을 연결한 새 작업으로 시작합니다.
- 후속 작업은 이전 요약·근거·작업 파일을 이어받고 전체 모델 대화를 재전송하지 않습니다. 이전 솔루션 후보는 작업 공간의 `previous/<작업 ID>/`에 복사합니다. 문제 자료·검증 코드가 변경됐으면 새 작업을 요청해야 합니다.
- 요청당 예산은 아래 기본값을 적용합니다. 후속 요청은 새 예산으로 시작하고 이전 사용량을 보존합니다. 동일 자료·목표·부모 작업·모델·엔진 버전은 같은 공유 결과를 재사용합니다. 같은 문제에도 여러 독립 작업을 등록할 수 있습니다. 자유 요청의 대기/실행 분석 합계가 20개이면 새 요청을 제한합니다. 기본 `VERIFICATION_AI_CONCURRENCY=3`으로 모델·도구 단계를 병렬 처리하며, PostgreSQL claim과 일일 예산 예약은 원자적으로 처리해 중복 호출을 막습니다.
- 중지는 다음 모델/도구 실행을 막습니다. 이미 시작한 외부 요청이나 격리 명령은 종료를 기다리며 해당 사용량과 실행 기록을 보관합니다. 공식 제출은 취소하지 않습니다.
- 작업 완료는 모든 입력의 정답 증명이 아닙니다. 최종 솔루션 후보의 전체 등록 테스트 실행을 검사하며, 실행하지 못했으면 `inconclusive` 결과와 제한을 남깁니다. checker·validator는 등록된 원본 그대로 검토합니다.

조회/다운로드는 `contest.problem.resource.view`, 요청/중지는 추가로 `contest.problem.test` 권한이 필요합니다. API는 `/operator/contests/{cid}/problems/{pid}/verification-tasks`의 목록·생성, `/{task_id}` 상세, `/{task_id}/stop`, `/{task_id}/workspace.zip`입니다. 문제 삭제 시 작업·분석·실행 연결도 삭제합니다.

## 동작

1. 실제 채점기가 작업을 가져갈 때 지문·해설·제한·활성 테스트 버전·파일 체크섬을 기록합니다.
2. 기본 모델에는 문제명, 판정, 실패 번호, 파일 ID와 예산만 전달합니다. 전체 소스나 테스트를 한 번에 프롬프트에 넣지 않습니다.
3. `list_files`, `read_file`, `search_file`, `read_image`, `inspect_judge`로 필요한 파일과 부분을 조회합니다. 문제·해설·원본·실패 입출력을 먼저 비교하고 필요하면 checker, validator, 등록된 다른 검증 코드를 확인합니다.
4. `edit_code`는 정확한 문자열 치환으로 별도 후보를 만듭니다. 파일을 직접 수정하지 않습니다.
5. `run_code`는 원본·후보·참조 코드를 선택 테스트 또는 전체 등록 테스트로 실제 실행합니다. 기존 isolate 샌드박스, checker, 언어별·케이스별 제한을 사용합니다. 원본 재실행과 최종 후보의 전체 테스트 실행 없이 정상 완료 보고서를 제출하지 못하도록 검사합니다. 예산/환경 문제로 끝난 작업은 미완료 범위를 남깁니다.
6. `run_probe`는 AI가 제안한 입력·기대 출력을 임시로 실행합니다. 공식 테스트에 등록하지 않습니다. **기대 출력은 AI 가설**이며 validator를 자동 실행하지 않습니다. 참조 코드도 반드시 정답이라고 간주하지 않습니다.
7. 채점 대기에는 모델을 호출하지 않습니다. 서버가 결과를 확인한 뒤 도구 결과를 전달합니다. 실행 뒤에도 모순이 해결되지 않을 때만 예산 내에서 `escalate`로 상위 모델을 한 번 사용할 수 있습니다.
8. 보고서에서 실제 실행, AI 해석, 미검증 후보·반례, 확인하지 않은 자료를 구분합니다. 후보 코드를 내려받을 수 있습니다.

전체 등록 테스트 통과는 모든 입력에 대한 정답 증명이 아닙니다. testlib.h·등록된 checker·validator·package-resource는 읽기 전용 채점 기준입니다. 복사본은 파일 도구에서 변경·삭제할 수 없고, gVisor 안에서도 root 소유 파일과 sticky 디렉터리로 교체·이동을 막습니다. 실행 후에도 파일 해시를 확인합니다. 기준의 오류가 의심되면 원본으로 최소 반례를 재현해 보고하며 기준을 고쳐 통과시키지 않습니다. 기존 채점기 도구는 등록된 원본 checker를 유지합니다. 코드 실행은 격리 실행 도구로만 허용되며 백엔드 호스트 명령 실행이나 외부 URL 조회는 없습니다.

## 모델과 비용

기본은 `gpt-5.4-mini`의 low reasoning, 상위 검토는 `OPENAI_MODEL`(기본 `gpt-5.4`)의 medium reasoning입니다. 간단한 파일 탐색·대기에는 상위 모델을 쓰지 않습니다. 상위 모델 전환 시 실제 실행 근거와 파일 목록으로 짧게 인계합니다.

기본 한 분석 예산:

| 항목 | 한도 |
|---|---:|
| 예상 API 비용 | $0.20 |
| 누적 입력 / 출력 토큰 | 60,000 / 16,000 |
| 모델 호출 / 도구 호출 | 10 / 48회 |
| 실제 추가 채점 | 6회 |
| 전체 시간 | 15분 |
| 이미지 | 2개, 각 1 MiB, 낮은 해상도 |
| 조회 범위 | 한 번에 12,000바이트 |
| 파일 읽기 | 파일당 최대 32 MiB, 전체 SHA 검증 후 필요한 부분 전송 |
| 수정 후보 | 4개, 각 128 KiB |
| 제안 반례 | 입력·출력 각 8 KiB |

요청 전에 보수적인 입력 토큰 상한과 최대 출력 비용을 예약합니다. 처음에는 UTF-8 바이트 수를 사용하고, 다음 요청부터 모델·지침·도구·기존 대화가 모두 같으면 API가 측정한 기존 입력 토큰 수에 새 내용의 상한을 더합니다. 한국어 지침 전체를 매번 바이트 수로 중복 추정해 보고서 작성 전에 조기 중단되는 것을 방지합니다. API가 반환한 실제 토큰과 캐시 사용량으로 예상 비용을 갱신합니다. 요청 응답이 유실되면 최대 사용량을 보수적으로 기록하여 수동 재시도가 예산을 우회하지 않게 합니다. 한도 도달 시 확인된 기록을 저장하고 중단합니다. 세금·환율·프로젝트별 요금 차이는 포함하지 않습니다.

등록 요금(100만 토큰, USD, 표준 API): mini 입력 0.75 / 캐시 입력 0.075 / 출력 4.50, gpt-5.4 입력 2.50 / 캐시 0.25 / 출력 15.00. 요금이 등록되지 않은 모델은 비용 통제를 위해 호출하지 않습니다. 요금 변경 시 서버 가격표도 갱신해야 합니다. [mini 공식 문서](https://developers.openai.com/api/docs/models/gpt-5.4-mini), [gpt-5.4 공식 문서](https://developers.openai.com/api/docs/models/gpt-5.4).

일일 분석 시작 한도는 기본 50회(UTC)이고 실패·수동 재시도도 집계합니다. 진행 중인 작업은 날짜 한도와 별개로 자신의 예산 안에서 계속됩니다. 자동 유료 재시도는 하지 않습니다. 동일 분석 수동 재시도는 최대 3회이며 기존 누적 비용·토큰 예산을 유지합니다.

## 캐시와 채점 부하

검증 코드의 채점 요청은 제출 생성과 같은 DB 트랜잭션에서 파일에 연결됩니다. AI 분석 요청 여부나 API 키 설정과 무관하게 판정·실패 테스트 번호·입출력/컴파일 로그·실행 시간·메모리·요청 시각·요청자를 서버에 보관합니다. 화면은 파일별 가장 최근 요청의 채점 상태와 그 제출에 연결된 AI 분석을 조회합니다. 이전 요청이 늦게 완료되어도 최신 요청을 덮어쓰지 않습니다. 재진입·새로고침·창 복귀 시 서버 기록을 갱신하며, 완료 결과는 브라우저에 남은 진행 상태나 조회 오류보다 우선합니다. 문제 자료가 바뀌면 이전 기준 결과임을 표시합니다. 조회에는 기존 문제 자료 열람 권한이 필요합니다.

0039 마이그레이션은 이전 버전의 미연결 운영자 채점 중 같은 대회·문제의 파일 SHA-256과 소스가 정확히 일치하고 파일을 하나로 특정할 수 있는 기록을 복원합니다. 파일 등록 전 제출, 중복 파일, AI 실험 제출은 연결하지 않습니다. 요청 시각과 원래 판정·로그를 보존하고 AI 분석은 생성하지 않습니다. 과거 스냅샷이 없는 기록은 원본 기준을 추정하지 않으며, AI 분석을 원하면 다시 채점해야 합니다.

같은 대회·문제 자료·소스·판정·진단·모델·엔진 버전이면 보고서를 공유합니다. 시간/메모리 초과와 관련 없는 판정에서는 실행 시간 1ms나 메모리의 작은 변화로 캐시를 무효화하지 않습니다. 동일 분석의 같은 코드·테스트 범위 실행도 재사용합니다. GET 조회나 화면을 펼치는 동작에는 새 API 비용이 발생하지 않습니다.

AI 추가 채점은 일반 제출보다 낮은 우선순위이며 전역에서 대기·실행 합계 2개까지만 만듭니다. 기존 점수·순위·일반 제출 목록에는 포함하지 않습니다. 문제 자료가 변경되면 추가 실행을 거절하며, 큐에 넣은 뒤 채점기가 가져갈 때도 버전을 다시 검사합니다. 선택 테스트/임시 반례 실행에서는 전체 테스트 번들을 적용하지 않습니다.

기존 정적 분석은 유지됩니다. 최신 자료와 같은 기존 보고서에서 **실제 채점으로 검증**을 누르면 새 에이전트 분석을 시작합니다. 판정 불일치만으로 분석을 생성하거나 모델을 호출하지 않습니다. 명시적 요청 시각이 있는 분석만 워커가 처리합니다. 전환 전에 자동으로 쌓인 미시작 분석은 버튼 입력을 기다리고, 이미 시작한 작업과 자유 요청은 이어집니다. 이미 성공한 과거 분석을 일괄 유료 재분석하지 않습니다.

## 서버 설정

운영 환경파일: `/home/zoj/zerone-online-judge/backend-v1/deploy/env/backend.env`.

```dotenv
OPENAI_API_KEY=서버에서만_설정
OPENAI_MODEL=gpt-5.4
VERIFICATION_AI_ENABLED=true
VERIFICATION_AI_DAILY_LIMIT=50
VERIFICATION_AI_CONCURRENCY=3
VERIFICATION_AI_TIMEOUT_SECONDS=180
VERIFICATION_AGENT_ENABLED=true
VERIFICATION_AGENT_MODEL=gpt-5.4-mini
VERIFICATION_AGENT_MAX_COST_USD=0.20
VERIFICATION_AGENT_MAX_INPUT_TOKENS=60000
VERIFICATION_AGENT_MAX_OUTPUT_TOKENS=16000
VERIFICATION_AGENT_MAX_CALLS=10
VERIFICATION_AGENT_MAX_TOOLS=48
VERIFICATION_AGENT_MAX_RUNS=6
VERIFICATION_AGENT_TIMEOUT_SECONDS=900
```

API와 verification-ai-worker 모두 환경변수를 적용해야 합니다. 단순 restart는 환경변수를 갱신하지 않습니다. 기존 blue/green 배포 스크립트는 검증 워커를 먼저 정리하고 API 전환 후 새 워커를 시작합니다. 키 값은 Git, VITE 환경변수, 로그에 넣지 않습니다. 키를 비워도 저장된 보고서는 계속 조회됩니다. `VERIFICATION_AGENT_ENABLED=false`는 새 분석을 이전 정적 방식으로 처리합니다.

권한: 조회는 `contest.problem.resource.view`, 수동 요청은 추가로 `contest.problem.test`. 숨겨진 테스트·코드가 포함될 수 있어 참가자나 일반 검수자에게 공개하지 않습니다. 임시 실행도 일반 제출 조회로 유출되지 않게 분리합니다. 문제 삭제 시 분석·실행 연결 기록도 삭제됩니다.

출제 자료에서 선택한 내용은 OpenAI API로 전송됩니다. 파일 내부의 개인정보/비밀은 자동 제거하지 않습니다. 문서·코드의 지시는 데이터로 취급합니다. `store:false`로 요청하고 도구 호출 이력은 ZOJ DB에 checkpoint로 저장합니다. 성공 시 모델 대화는 삭제하고 보고서·실행 근거·수정 후보만 남깁니다. [함수 호출 문서](https://developers.openai.com/api/docs/guides/function-calling).

## 지연·실패 점검

- ‘실제 채점 대기’: 활성 채점기/기존 참가자 대기열을 확인합니다. 이 동안 추가 모델 비용은 없습니다.
- ‘자료 변경’: 최신 자료로 원본을 다시 채점하세요.
- ‘일부 검증 후 종료’: 비용·토큰·시간·실행 한도와 실제 기록을 확인하세요. 미검증 후보를 정답으로 간주하지 마세요.
- API 응답 유실/중단: 자동 과금 재시도하지 않습니다. 진행 중 claim이 5분 이상 남으면 실패로 정리합니다. 수동 재시도도 같은 누적 예산을 유지합니다.
- 키/모델/결제 문제: API와 워커의 키 설정 및 프로젝트 모델 권한을 확인하세요. 원문 오류·키는 로그에 출력하지 않습니다.

```sh
docker compose -f deploy/compose.backend.yaml ps verification-ai-worker
docker compose -f deploy/compose.backend.yaml logs --tail=50 verification-ai-worker
```

## 자체 서버 플레이그라운드

사용자의 파일 생성·삭제·수정·반복 실행 요구를 위해 별도 `playground-control` 서비스를 추가했습니다. 작업별 파일 내용과 실행 권한을 분석 상태에 보관하며 `workspace_copy/write/patch/read/list/delete` 도구로 조작합니다. `workspace_exec`는 한 번에 명령 1개를 새 gVisor 컨테이너에서 실행하고 결과 파일만 돌려줍니다. Python으로 반례 생성기·기준 풀이를 작성하거나 C/C++·checker·validator를 컴파일해 대조 실험할 수 있습니다. `workspace_candidate`로 최종 코드를 기존 채점기에 넘깁니다. 작업 파일 ZIP과 실험 명령·출력도 권한 있는 운영자가 공유합니다.

토큰 절약: 파일 복사는 모델에게 내용을 전부 보내지 않습니다. 많은 작은 테스트를 한 스크립트로 실행해 차이·통계만 짧게 출력할 수 있습니다. 플레이그라운드 자체에는 OpenAI 컨테이너 요금이 없고 서버 자원을 사용합니다.

- gVisor 런타임이 없으면 실행을 거절합니다. 일반 Docker나 백엔드 호스트 실행으로 대체하지 않습니다.
- 실행 컨테이너에는 호스트 볼륨, Docker 소켓, API/DB 키를 전달하지 않습니다. 네트워크를 끕니다. 제어 서비스만 Docker 소켓을 가지며 포트를 외부에 공개하지 않습니다. 제어 API는 별도 임의 토큰으로 인증합니다.
- 컨테이너당 CPU 1개, RAM 768 MiB, PID 64개, 임시 파일 시스템 각 32 MiB, 명령당 1~30초, 분석당 실행 시도 12회, 전역 동시 실행 2개입니다(`PLAYGROUND_CONCURRENCY`, 범위 1~4). 같은 실행 ID는 병렬 호출돼도 중복 실행하지 않습니다. 명령은 별도 비특권 UID로 실행하고 종료 후 백그라운드 자식도 정리합니다.
- 작업 파일은 48개·파일당 256 KiB·합계 2 MiB까지 보관합니다. symlink·특수 파일은 보관하지 않습니다. 출력은 12,000바이트까지만 남깁니다. 한도 초과 파일은 제외 사실을 표시합니다.
- 요청 ID로 중복 실행을 막으며 24시간이 지난 제어 서비스 응답 캐시는 다음 실행 요청 때 정리합니다. 분석 DB에는 공유 보고서와 작업 파일을 보관합니다.
- Python 3.13, GCC/G++, Java 17을 제공합니다. 기존 채점기의 Java 8 및 자원 제한과 다르므로 시간/메모리 적합성은 기존 채점기의 최종 판정으로 확인합니다.

최초 설치는 **ZOJ 애플리케이션 VM**에서 관리자 권한이 필요합니다. 별도 서비스 코드가 배포된 뒤 실행하세요.

```sh
cd /home/zoj/zerone-online-judge/backend-v1
sudo bash deploy/setup-verification-playground.sh
```

공식 gVisor 배포 파일과 SHA-512를 확인하고 `runsc` 런타임을 추가합니다. 기존 Docker 설정을 백업하고 `systemctl reload docker`를 사용하며 기존 API 컨테이너를 재시작하지 않습니다. 실행 이미지를 빌드하고 전용 토큰을 생성해 제어 서비스 및 검증 워커만 기동/재생성합니다. 이후 일반 배포에서도 설치된 플레이그라운드 이미지를 함께 갱신합니다. 참고: [gVisor 설치](https://gvisor.dev/docs/user_guide/install/), [격리 개요](https://gvisor.dev/docs/).
